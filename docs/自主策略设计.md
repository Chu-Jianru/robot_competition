## 当前入口

`ros2 launch sweep_robot sim.launch.py` 默认启动 Gazebo、HSV 感知、`adaptive_controller`。控制节点名称仍为 `follow_path`。按空格开始；批量验证加 `autostart:=true gui:=false show_window:=false`。

## 决策方式

开局先留出0.4秒观测运动趋势，再识别当前画面是否仍是两条完整横排，且横推通道没有对手占位。符合条件时，车头在西南空区转向东，从西侧依次连续推对方一排、己方一排，将散布在整条横排上的块集中到东侧，再从南侧转向北沿墙推出己方半区。

整排任务持续复查尚未执行的完整横排通道，对手在远处进入后续任务区域时就提前取消，不等它靠近车身才退让。西侧窄入口退出再次受阻时保留恢复路径，不能把朝东车辆留在入口内交给北向局部规划。

整排任务由实时视觉反馈推进，每段都有到位、航向、净空、进展和时间预算检查。第二排开始前重新拟合当前排的位置；若队形散开、对手进入通道或没有进展，则取消开局任务并转入局部清理。刷前连续积木队列接近东墙时提前减速并结束该铲，避免强行把车心推到固定坐标而挤散积木。西侧窄入口只允许朝东进入，取消任务时先沿入口退出，在空区转向。

局部清理持续观察己方红块和未知大物体，比较可推车道的可清除量、接近距离、推送时间、对手预测占位和路径可达性，然后完成一铲、重新评估。整排开局只尝试一次，不能在散乱残局中反复重启长路线。

可清除量按滚刷对物块的实际覆盖率加权，对仅擦到块边缘或可能蹭到邻块的车道降分。对齐误差收敛后才开始推送，不用“靠近某条道”代替刷子真正罩住物块。

- 己方红块优先。红色长条即使中心已越过中线，只要外沿仍跨入己方，也继续列入候选。
- 横推阶段车头朝东、沿墙及局部清理车头朝北；空区完成大幅移动和转向，块带内只做很小的纠偏。
- 推完后先退出刷子接触，再检查从当前车道或其他较宽出口返回南侧。所有路段都检查净空，不假设旧路线永远畅通。
- 直接通行不可行时使用小场地网格搜索，并做可见性简化。网格包含当前坐标，支持窄出口先直退。搜索有耗时上限，不以长时间阻塞控制来换取路径。
- 目标短时不可达或没有进展时，暂时降低该列优先级并比较其他列。不会循环发送预设的随机挪车动作。

规划和速度安全检查共用按当前航向投影的底盘、滚刷、斜导板轮廓。搜索网格还加入障碍间空隙的中心线，降低粗网格漏掉窄通道的概率。快速搜索未完成时，在后台继续有预算的全局搜索；控制和看门狗继续执行停车，接受结果前再对照最新场景复查。过时路径不能在比赛结束后重新启动车辆。

如果红块封住退路，程序会比较附近可完整覆盖的物块，在空隙中对准后直推一小段腾出通道，再继续清理己方。这个动作会避开对手占位和贴墙堆，不能用推撞未知机器人替代清障。

未知物体按位置、大小和最近视觉运动关联跟踪。未来约 0.8 秒的可能扫掠范围作为障碍。对手占据推送走廊时，暂停该铲、退让或改列；近距离冲突时，比较能增加净空的退让速度。若被顶偏，先脱离近处物块，再恢复航向。车身净空按实际朝向和前后不同长度计算。

对近中线横穿的对手，区分“预计会经过车道”和“即将撞到当前车辆”。已经位于扫掠带南侧且当前净空足够时，保留已选车道等待空档，最多2.5秒，避免反复退开、重新对准。对手出现向己方靠近的纵向速度、侧后有来块或当前净空不足时，立即恢复退让。推送终点也缩短到能越过中线及横穿扫掠带的位置，减少不必要的深入；静态和其他对手仍使用原深推终点。

对动态红块检查未来0.25、0.5、0.75与1秒的位置，避免只查1秒终点、漏掉中间已经穿过车体的来块。

连续观测确认静止至少0.7秒后，邻接通道采用较小的额外退让余量；一旦开始运动，立即恢复动态余量。不能把静态障碍旁可通过的结论直接用于横穿对手。直退会扫到斜导板角时，还会比较先小幅斜退脱离、再沿空区返回的通道；这些是有净空检查的完整路径。

红块也估计最近的视觉运动，用于提前发现对手推向车体侧后方的动态物块。若退路被挤占，而车头已经朝北，可用严格限制横向速度的直推脱离包围；这一动作仍只允许滚刷、导板和腔体接触。不会因为处于退让状态就禁止所有合法前推，把车困在前后物块之间。

这属于基于观测的规划与反馈控制，没有训练神经网络，也没有预知对手下一步动作。脚本对手只用于验证，不为己方控制器提供对手真实位姿。

## 清空后与时限

一次空检测不会将比赛永久标为完成。检测目标有短时遮挡记忆；己方暂时清空后，车辆尽可能退回空区待命，继续接收新画面。对手将红块推回来时会再次选道清理。

90 秒到时立即发零速，结束状态不再被新红块唤醒。比赛计时从启动后的第一个控制周期开始，不因丢帧暂停。

无效场地、没有新的车体检测、场景超过 0.35 秒未更新时停止。独立墙钟看门狗在图像流/仿真时钟异常时也会发零速。恢复感知后，未超过比赛时限则继续决策。

## 感知与标定

相机仍为 640×480、10 Hz，感知仍是 OpenCV HSV。蓝黄地面决定场地区域与归属，不拿场地几何中心冒充颜色分界。

四角由每条边中段的地面轮廓拟合直线，再外推被车或物块挡住的角。四角锁定不再因为单角持续遮挡就接受歪掉的场地。蓝黄分界优先采样两种颜色相邻的位置，降低整片地面遮挡面积改变带来的偏差。

障碍检测只擦除己方车身投影，不再直接丢弃距车心 16 cm 内的整个未知物体。保留障碍外接尺寸供控制规划使用。

Gazebo 发射文件为明确的正俯视相机设置 `camera_height=2.55`，按车顶标记 0.055 m、方块顶面 0.020 m 校正平面投影视差。单独启动 `hsv_detector` 时此参数默认 0，表示没有这项标定。实车倾斜相机不能直接套用该高度修正，需要实际标定。

原有话题继续保留。新增 `/perception/scene`（`std_msgs/String` JSON），每条消息来自同一张原始图像：

```json
{
  "stamp": 12.3,
  "valid": true,
  "robot": [0.1, -0.2, 1.57],
  "blocks": [[0.1, -0.05, 0.01, 0.01, true]],
  "obstacles": [[0.3, 0.02, 0.06, 0.07]]
}
```

`robot=null` 表示本帧没有新的车辆检测。物块为 `[x,y,半宽x,半宽y,己方标志]`，障碍为 `[x,y,半宽x,半宽y]`。时间戳与控制时钟必须同源；比赛实机调用纯策略时也必须遵守这一点。

## 运动与接触

普通运动对速度、加速度和加速度变化做限制，避免指令方向突然改变导致来回摆动。对准时等待横移基本收敛再开始推送。每一条实际待发布速度在平滑之后再次检查，包括刹停前瞻、红块净空、对手扫掠和围栏边界。

仿真时钟通过 `config/gazebo.yaml` 显式设为100Hz，以支持20Hz控制周期；相机仍为10Hz。这修正了插件默认10Hz时钟下控制定时器成批触发的时序问题。默认频率及参数机制见 [Gazebo ROS 初始化插件源码](https://raw.githubusercontent.com/ros-simulation/gazebo_ros_pkgs/ros2/gazebo_ros/src/gazebo_ros_init.cpp)。使用参数文件传参，避免与 Gazebo 自带 `-p` 回放参数冲突。

Gazebo 使用 `--lockstep` 和相机 `always_on` 保持传感器更新节拍，并限制软件渲染工作线程，避免后台旧渲染进程与仿真争用资源。没有降低相机频率或延长过期视觉容忍时间；渲染仍跟不上时停车。

仿真图像订阅使用可靠传输（`reliable_images=true`），避免大图分片丢失造成整帧丢弃；默认Gazebo发布器支持此设置。单独启动感知时仍默认best effort，兼容其他传感器发布器。队列深度1，只保留最新帧；检测进程限制为单个OpenCV工作线程。场景记录 `publish_stamp` 和 `processing_ms`，策略状态记录 `scene_age`，用于区分处理延迟、视觉失效与几何安全停车。

安全停车可以直接覆盖平滑，因此不能将这项设计表述为所有情况下速度导数都连续。对手突然撞入、视觉中断等情况下，停车优先。

控制不订阅 `/odom`，不对速度积分推算车辆位置。测试观察器可以读取里程计和 Gazebo 接触，用于独立验收；这些数据不进入比赛策略。

## 源码分工

- `row_policy.py`：两排队形识别、横向整排任务、顶墙收手、实时重拟合与退出恢复。
- `competition_policy.py`：纯 Python 场景记忆、障碍跟踪、选道、通行规划、运动平滑、实际航向净空、退让与比赛状态机。
- `adaptive_controller.py`：ROS 场景/速度/状态适配、空格启动、独立看门狗、退出停车。
- `field_vision.py`、`hsv_detector.py`：场地与颜色感知、场景消息、显式相机高度校正。
- `/strategy/status`：仿真时刻、状态、原因、当前车道、候选己方检测数与速度。这里的数量是视觉区域数，不是真实木块数量。


生成带脚本对手的测试场地，不覆盖正常世界：

```bash
python3 competition_robot/models/competition_robot/build_robot.py \
  --seed 20260922 --opponent cross --output-dir log/test_cross_world
python3 src/sweep_robot/test/run_sim_audit.py \
  --world log/test_cross_world/competition.world \
  --opponent cross --output log/test_cross_run
```

同版本逐列对照保持其余参数不变，验证器增加 `--rows-off`；普通启动对应 `sweep_rows:=false`。对照也必须完整跑90秒并逐块核对，不能拿不同图像传输条件下的耗时直接比较。

对手类型：`block` 为中线右侧占位，`cross` 为横向拦截，`return` 为在不同列向己方连续回推。`--dropout` 会在仿真 12～14 秒暂停检测节点，验证失帧停车与恢复。

验证器从比赛前开始订阅，独立原生Gazebo观察器持续记录20个块与己方车的真实位置，以94秒附近完整快照计数并保存，额外记录首次真实清空时刻。这样避免反复创建模型查询连接引发Gazebo transport断言崩溃。`--contacts-binary` 可接入 `test/contact_audit.cpp` 编译出的诊断程序，按碰撞部件审计真实接触，并独立记录模型位置。接触日志只保存与己方车有关的物块/对手接触，不保存海量地面接触；模型位置与接触诊断均不参与控制。不带原生观察器时仍保留串行查询方式，稳定性较差，不用于本轮正式矩阵。

正式测试使用独立 `ROS_DOMAIN_ID=46`、`GAZEBO_MASTER_URI=http://127.0.0.1:11365`，避免混入已经打开的比赛世界；观察器拒绝把启动前已运行超过2秒的旧时钟作为新比赛。默认演示窗口使用域0与端口11345。

图像传输排查依据：[Gazebo传感器同步说明](https://classic.gazebosim.org/tutorials?cat=sensors&tut=lockstep_physics_sensors)、[相机插件源码](https://raw.githubusercontent.com/ros-simulation/gazebo_ros_pkgs/ros2/gazebo_plugins/src/gazebo_ros_camera.cpp)。本机短测结果在 `log/row_strategy_20261021/reliable_probe.json`；可靠接收后9.8秒收到99帧，相邻帧间隔0.1秒。

## 能力边界

当前场景验证是指定尺寸、灰色外观的脚本对手和两个初始布局，不是对所有对手策略的证明。永久堵住车道时允许等待、清理其他列，不能声称一定清空。对手主动撞入时仍可能发生车车接触。

最终版在强横穿干扰下仍会频繁退让、重选车道，运动连贯性和清理效率比无对手时差；另一布局的连续回推也存在未清完的块。这两类情况仍有改进空间，不能把普通清场的平顺表现推广到持续对抗。虚拟机渲染出现长时间丢帧时，控制按既定时效阈值停车，不能通过沿用过期位姿维持表面上的连续运动。

连续回推场景中，视觉检测会合并或遮挡，不能用视觉区域数代替真实比分；验收必须查看逐块真实位置。未知物体的外观与地面/红块/己方色标高度相同时，HSV 区分存在局限。

本策略原仿真阶段没有完成现场无线协议、单片机执行和麦克纳姆轮速分配，也没有验证实车动力学。旧 `archive/legacy_esp32/` 通信与轮速分配草稿已于 2026-11-03 删除，执行链路以 [交接说明](../交接说明.md) 为准，尚未接入本策略或完成实车验收。正常程序继续只依赖视觉；实车部署前需要标定相机、确认车身面积测量口径并接通执行链路。
