# 项目盘点与下一步计划

> 2026-11-02 更新目录引用；下文功能与验收结论仍为 2026-10-22 盘点。现用底盘为 `hardware/workbench/`，旧草稿 `archive/legacy_esp32/` 已于 2026-11-03 删除，当前状态统一见 [交接说明](../交接说明.md)。

日期：2026-10-22（北京时间）。范围：`E:\robot_competition` 内所有顶层目录、功能包、导入工作台的源码子工程及主要入口。只做源码/文档/依赖检查和文件哈希核对，未连接串口、启动相机、烧录、运行电机或恢复仿真，没有删除或移动现有项目。

## 核心判断

目前有三块可继续使用的基础：Windows取图与视觉、MECANUM_V2实车底盘、纯Python比赛策略。它们尚未组成一条实机自动比赛链路，主要工作是接口整合、实物标定和闭环验收。

用户在本轮明确确认：**正在使用机器人调试工作台，前进、横移、转向均已实车跑通**。这更新了旧交接中“底盘没有真实运动结果”的判断；不据此推断轮速PID、无线控制、精度或自动推块已完成。

能从文件判断用途与依赖，无法仅凭目录名称确定作者归属。“导入交付包”不等于无用demo。

## 各项目的定位与去留

### 1. `windows/`：继续开发的实机视觉主线

已有 Mate60 Pro → USB → scrcpy-server → PyAV/OpenCV 的直接取图；保留最新帧，处理640×480、最多10Hz。

`red_blocks.py` 独立检测、颜色/像素尺度校准与形状筛选；`field_vision.py` 负责场地/色标；`scene_vision.py` 组合结果；`usb_camera.py` 提供B/F独立开关、K校准及S原图/标注图保存，物块框现为绿色。

上一轮18项离线测试、九张桌面原图复核通过，只说明现有样本；还没有完整实场地、多块粘连、车位/航向、持续视频及数字化端到端延迟验收。当前JSON是桌面拍摄尺度/光照配置，不能直接作为正式场地配置。

**结论：保留，作为唯一实机摄像头入口继续建设。** 不再另起一套相机客户端。

### 2. 导入的 `RobotDebugWorkbench-20261022-MECANUM_V2`：现用实机底盘主线

现位于 `hardware/workbench/`；队友 2026-11-02 的更新版（WHEEL_SPEED_V1，含轮速闭环）在 `vendor/`，两包的逐文件对应与差异见 [vendor 说明](../vendor/README.md)。本节描述的是 2026-10-22 那一版。

完整路径位于项目的 `hardware/workbench/`。下文称“工作台目录”。

- `source/motor-bringup/`：PlatformIO/Arduino实际固件；四路电机输出、四路正交编码器、STBY、定时停止、通信停止及X型麦轮混控。
- `source/debug-workbench/`：现用台架和麦轮界面、独立通道标定与日志，`main.py` 是统一入口。
- `source/esp32-pc-link/`：含旧DRY_RUN界面和客户端，也含**现用固件仍编译引用的 `lib/link_core`**。`motor-bringup/src/dry_core.cpp` 直接相对包含该核心；统一工作台也导入其中的界面/主题/相机模块。不能因名称像演示而整目录移除。
- `source/release_tools/`：打包、自检和交付工具，不是另一套机器人控制器。
- `app/`：已打包的Windows程序；`_internal/` 是其运行依赖，不是另一个项目。`third_party_licenses/` 为依赖许可。

本轮逐项核对 `release-manifest.json` 中1210个文件，哈希全部一致；包外的两个文件是清单本身和 `SHA256SUMS.txt`。这验证本地交付包一致性，不代表板上固件已被本轮读取。包内86项Python回归、C++检查、此前烧录及静止查询是其历史记录，本轮没有重跑。用户本轮补充了三种基本运动的实车结果。

**结论：保留并作为实际电机驱动开发起点。** 开发修改源代码，重新构建后再更新EXE，不能认为编辑Python会自动更新已有EXE。

### 3. `archive/legacy_esp32/`：旧Wi‑Fi控制草稿，退出当前实机主线（*已于 2026-11-03 删除，以下为当时的盘点记录*）

三个文件为旧 `.ino`、`esp32_link.py` 与 `test_motion.py`。虽然具备UDP示例、速度到PWM比例、示例逆解及超时停车，但没有编码器闭环；其GPIO、STBY处理、供电假设与现用FOUR_V1不同。

例如旧草稿把GPIO25/26用于电机输出，现用接线已把它们分配给C路编码器。**不能给当前接线直接烧录旧 `.ino`，也不能把旧UDP客户端视为兼容现用固件。** 可借鉴UDP收发和坐标转换思路，后续统一到现用固件；本轮不删除。

### 4. `src/sweep_robot/`：策略资产与ROS适配混合包

- `competition_policy.py`、`row_policy.py` 为纯Python比赛策略，可复用；已有路径选择、横排推送、净空检查、90秒硬截止及视觉过期停车等逻辑。
- `adaptive_controller.py`、`hsv_detector.py`、`launch/` 是ROS适配，不是Windows实机入口。
- `follow_path.py` 是旧控制对照；`push_blocks.py` 是早期自动推块方式。`teleop_keyboard.py`、`record_trajectory.py` 是手动/记录工具。保留作历史与测试用途，不再增加另一条实机控制主线。
- `mecanum_ik.py` 是带 `NotImplementedError` 的旧教学模板，文案仍提STM32。现用ESP32已有百分比混控，不能把此模板的缺失等同于“实车完全没有麦轮分配”；也不能把百分比混控当成物理单位轮速逆解。

策略中的车宽、滚刷、导板、腔体和接触轮廓来自仿真，需要按真实车辆和实际推块机构重新测量。没有验收实物几何前，不能直接将原速度交给真实底盘。

**结论：复用策略与测试，新增Windows适配；ROS入口保留在仿真侧。**

### 5. `competition_robot/`、`src/sweep_robot_gazebo/`：仿真专用

场地、车体生成器、Gazebo模型与防倾覆插件均有明确用途，不是Windows比赛运行时依赖。h15仍保持暂停；历史记录中cross/return/return2完成，block中断，最终矩阵未完成。

## 开发板与当前硬件基线

已通过浏览器读取用户提供的[开发板资料](https://szytf.yuque.com/igocfe/ho0nid/bqr399ep5s3vzrcm?singleDoc)。资料说明ESP32-WROOM-32、2.4GHz Wi‑Fi、3.3V GPIO、USB5V供电，USB接口和CP2102/CH9102等芯片随批次变化；不能按商品编号猜出精确批次，也不能默认具有PSRAM。

**我的判断：可以继续使用这块ESP32，尚无必须更换主控的证据。** 视觉和策略由Windows承担，ESP32承担编码器采集、四路速度控制和通信。板级供电、电平及负载仍需按实物核对，模组规格不等于整车验收。

当前软件基线应采用工作台的FOUR_V1/MECANUM_V2：

- 轮位FL/FR/RL/RR = A/D/B/C，布局符号全+1。
- A/B/C/D底层电气极性 = -1/+1/+1/-1，只在驱动层修正一次。
- A的IN1/IN2/EA/EB = 21/19/22/23；B = 16/4/17/18；C = 27/14/26/25；D = 32/33/35/34；STBY=13。
- 当前方案在IN1/IN2输出PWM，驱动板专用PWM固定接其自身5V；这与旧 `.ino` 的方案不同。保持已跑通配置，不能混抄两套接线。
- GPIO34/35为编码器输入，符合[Espressif GPIO说明](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/peripherals/gpio.html)的输入限制；它们没有内部上/下拉。GPIO16/17是否可用还需以WROOM实际版本及模组占用为准，不能套WROVER的PSRAM保留说明。
- 旧交接提2串7.4V电池，而现用工作台文档记6V电机输入；需确认当前降压后的母线及带载压降，不把两条记录合并为已验证供电值。

工作台自身还记录了3.3V直接驱动5V逻辑的待核实项。如果D24A上的TB6612逻辑VCC实际为5V且没有电平转换，东芝规格给出的高电平最低值为0.7×VCC，即3.5V，ESP32的3.3V不能据此保证合格；**这是基于芯片规格的条件判断，不是对板级电路的实测结论**。应核对D24A原理图/实际VCC再决定处理，不在本轮盲目改线。[TB6612FNG官方规格书](https://toshiba.semicon-storage.com/info/docget.jsp?did=10660&prodName=TB6612FNG)

## 尚未接起来的关键接口

1. 真实底盘的 `MECANUM x y z duration` 是百分比开环、定时单次动作。固件运行中拒绝下一动作，停止后有1秒冷却；它不能直接接10/20Hz持续速度更新。DRY_RUN的流式DRIVE虽有会话与序号，但刻意不驱动真实电机。
2. 策略需要车体 `vx,vy` 的m/s与 `wz` 的rad/s。现用z为旋转力度，不能通过改变量名当成rad/s，也不能用固定比例在所有负载下保证真实速度。
3. 主线固件目前是串口，没有现成的真实Wi‑Fi速度控制；旧UDP草稿不能直接顶替。比赛要求无线，需要在主线固件上新增通信层。
4. 编码器采集与PC显示已具备，但未找到本车四路每圈计数、原始相位符号、周期测速及轮速PID的完整验收记录。counts/s和PC估算RPM不等于MCU轮速闭环。
5. 当前红块能独立检测；自动推块还需要有效场地坐标、可靠车体位置与航向。用户暂不能加色标，既有品红/青色方案不能直接认定可用，需单独实现并验收无色标定位。
6. 仿真已有90秒和0.35秒场景过期停车；这些不能因换到Windows而丢掉。台架1.5秒通信看门狗不是等价的视觉新鲜度保护。

## 下一步顺序与完成标准

另有一份 2026-11-02 的阶段式路线图 [后续计划与比赛策略-2026-11-02.pdf](后续计划与比赛策略-2026-11-02.pdf)（4 页）：按 M0 基线 → M1 底盘 → M2 视觉 → M3 接口 → M4 单块 → M5 多块 → M6 对抗 → M7 定版推进，并给出"直接北推 vs 横向归拢后沿墙送"的 A/B 对照口径（净送出块数/秒、严重漏块、卡住时间、人工干预）。它是建议方案，验收数字是目标值，不能替代下文各阶段的实测标准；两套划分并行使用，不要机械对齐。

### 第一阶段：先把现用底盘变成可标定的速度执行器

优先工作是**用现有工作台完成四路编码器与机械参数核对**：确认每圈计数、前进时的计数正负、转速与PWM曲线、起转死区、轮径、轴距轮距和带载供电。已有参数先导出/核对，不重复猜测或覆盖。保存能追溯到具体通道的记录。

接着在 `motor-bringup` 现用驱动上增加MCU定周期测速及四轮速度闭环，保留统一极性和STOP逻辑。先证明每路目标/实际轮速可比较、负载变化下能收敛、停止后输出确实归零，再承诺车体速度。

### 第二阶段：增加面向自主控制的流式物理速度协议

保留手动台架模式，另设计新的自主模式与版本握手：一致的单位/坐标、会话、递增序号、指令有效期、最新目标覆盖、反馈、断联停车、比赛截止。先在串口验证，再接2.4GHz Wi‑Fi。不是删除busy/cooldown后直接连续调用现有按钮协议，也不是直接把DRY_RUN接到GPIO。

通过标准：指令连续更新、旧包不会复活运动、断网/进程结束/比赛结束停车；记录真实轮速和链路延迟，不能只看界面“已发送”。

### 可并行的视觉阶段：固定完整实场地，验收定位

固定相机拍完整1.2m场地，重新做对应高度/光照的红块校准，收集多块、贴车、墙边、粘连、遮挡和反光视频；分别记录漏检与误检。保持一个采集源。

在暂不贴标的约束下，先以人工确认初始车体/车头、自然外观模板或特征跟踪作为候选方案，实测位置和航向、失效检测与重定位能力。它是待实现/待验证方案，不是现成功能；定位丢失时保持停车，不能用速度积分冒充视觉位姿。

### 第三阶段：Windows策略适配与逐级联调

建立统一场景/时钟适配，复用 `competition_policy.py`、`row_policy.py`，按实物更新车身与推块机构几何，接新的物理速度接口。先只记录策略计算结果，再依次验收单块推过线、多块清理、90秒运行，以及图像中断/定位丢失/通信中断/比赛截止停车。

最终才安排整场与对抗验证；Ubuntu仿真继续保持暂停，另行获准后再恢复矩阵。

**当前最明确的下一项任务：四路编码器和机械参数核对、标定记录，然后实现MCU轮速闭环。** 视觉方面同步从桌面单块样本转到固定相机下的完整真实场地，优先补车体定位，不继续把所有时间花在单帧框颜色上。
